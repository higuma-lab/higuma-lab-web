## 決定事項

### D-001 公開タイミングと実績ページの方針（2026-10-08）

- 実績が揃うのを待たず、Windowsストア向けアプリの公開に合わせてサイトを公開する（アプリ公開前の場合は「公開予定」として掲載可）。
- 実績ページは「制作実績」ではなく「制作物・取り組み（Works）」とする。
- 各項目に種別ラベルを付ける：`自社プロダクト` / `サンプル制作` / `技術検証` / `お客様案件`。
- 件数より質を重視し、各項目は「課題 → 設計 → 技術 → 工夫点」の形式で記述する。
- 件数が少なくても成立するレイアウトにする。
- 初期掲載：本Webサイト、Windowsストアアプリ（アプリ名・概要とも公開可）、GitHub。経歴（匿名化）はプロフィールで示す。
- 公開後、以下を順次追加する：
  - 小規模事業者向けサンプルサイト 1〜2件（サンプルであることを明記）
  - 技術記事・ブログ（月1〜2本目安。AI活用事例を含む）
  - 掲載許可を得たお客様案件

**理由**：個人事業の初期集客は紹介・SNS経由が中心で、サイトは信頼確認の場として機能する。ドメイン評価の育成には時間がかかるため早期公開が有利。架空の実績は作らない。

### D-002 フレームワーク：Astro（2026-10-08）

- Astro + TypeScript（strict）で静的サイトとしてビルドする。
- ブログ・Works はリポジトリ内の Markdown/MDX（Content Collections）で管理する。CMS は導入しない。
- パッケージマネージャーは npm。

**理由**：コンテンツ中心でサーバー処理不要。JS を最小化でき、Core Web Vitals に有利。Markdown 管理は Claude Code での執筆・更新とも相性が良い。

### D-003 DNS・ホスティング構成（2026-10-08）

- ドメイン登録：お名前.com（`higuma-lab.jp`）。
- DNS管理：Route 53（お名前.com のネームサーバーを Route 53 に変更）。
- ホスティング：S3（非公開バケット、ap-northeast-1）+ CloudFront（OAC）。
- 証明書：ACM（CloudFront 用に us-east-1 で発行、DNS検証）。
- 正規URL：`https://higuma-lab.jp`（apex）。`www` は apex へリダイレクト。※Phase 2 で最終確認
- デプロイ：GitHub Actions（OIDC で AWS ロールを引き受け、アクセスキーは使わない）。
- IaC：AWS CDK（TypeScript）。

**理由**：Route 53 なら apex を CloudFront に Alias で向けられ、ACM の検証も自動化できる。CDK はサイトと同じ TypeScript で記述でき、再現性と技術実績を兼ねる。

### D-032 インラインのスクリプト・スタイルを出力しない（2026-10-08、Phase 4）

- `vite.build.assetsInlineLimit: 0` で、Astro が小さなスクリプトや画像を HTML にインライン化しないようにする。
- JS が無効なときのメニュー表示は、インラインの `<style>` ではなく `public/noscript.css` を `<noscript>` で読み込む。
- 例外：JSON-LD（`application/ld+json`）はデータで実行されないため CSP の対象外。

**理由**：Phase 8 の CSP（design.md 7.3）で `script-src`・`style-src` に `'unsafe-inline'` やハッシュを使わずに済ませるため。

### D-033 ブランチと PR の運用（2026-10-09）

- Phase 5 以降は、フェーズごとにブランチを切る（例：`phase-5-content`）。フェーズの終わりに push し、PR で `main` に取り込む。
- フェーズの途中の小さな修正（誤字、ドキュメントの追記）も、作業中のブランチに含める。フェーズの外で直すものは `fix/...`・`docs/...` のブランチにする。
- Phase 4 までのコミットは `main` に直接入れたまま、作り直さない。
- PR は自分でマージする（レビュー担当は置かない）。マージ方法は通常のマージコミット（フェーズ内のコミットの区切りを残すため）。
- Phase 8 以降、`main` への push はデプロイになるため、`main` に直接コミットしない。CI の通過をマージの条件にする（ブランチ保護の設定はオーナーが行う）。

**理由**：`main` への push でデプロイする設計（design.md 7.4）で、確認前の変更が本番に出るのを防ぐ。PR で CI が動き、公開リポジトリとして作業の履歴も見せられる。CI ができる前から同じ流れにしておき、Phase 8 での切り替えをなくす。

### D-034 SEO・性能まわりの実装方針（2026-10-09、Phase 6）

- **OGP 共通画像**：`scripts/ogp/build.mjs` で生成した PNG（`public/og/default.png`）をコミットする。ビルドのたびには作らない。
  - キャッチコピーの文字は、Windows に標準で入っている BIZ UDPゴシック（SIL OFL 1.1）で描く。フォントはリポジトリに含めない。
  - sharp は Astro の依存として入っているものを使い、サイトの依存は増やさない。
  - コピーやロゴを変えたら、スクリプトを実行し直す。
- **CSS** は1ファイルにまとめる（`vite.build.cssCodeSplit: false`）。インライン化しない設定（D-032）ではコンポーネントごとに分かれ、1ページで十数回の読み込みになるため。全ページで共通のファイルになり、キャッシュが効く（約 30KB）。
- **RSS**（`@astrojs/rss`）は、最初の記事を公開するときに導入する（D-017 の時期を変更）。記事が0本のフィードは出さない。
- **サイトマップ**には 404 を含めない。hreflang はページの `<link>` で示しているため、サイトマップの `xhtml:link` は付けない。
- **noindex のページ**（404）は、canonical・og:url・構造化データを出さない。

### D-035 テストの実装方針（2026-10-09、Phase 7）

- **リンク切れ**は自作スクリプト（`scripts/check-links.mjs`）にした。linkinator は使わない。依存を増やさず、ページ内リンク（`#id`）の移動先の有無や、本番 URL で書かれた canonical・hreflang・og:image も `dist/` の実ファイルと突き合わせられるため。外部リンクは対象外で、手動で確認する。
- **E2E の対象ページ**は `dist/` の `index.html` から自動で求める。ページを足してもテストの修正は要らない。
- **スマホの幅**は 360px（Pixel 7 のエミュレーションで幅だけ狭める）。375px 以上の機種もこれで代表させる。
- **axe** は WCAG 2.2 AA までのルールに加え、best-practice（見出しの階層、ランドマーク等）も違反0を条件にする。
- **E2E 用のサーバー**は astro preview を 4322 番、`--ignore-lock` で起動する（Astro 7 の preview はポートが違っても2つ目の起動を拒むため、開発用の preview と並べて動かせるようにする）。
- `npm run test:e2e` と `npm run test:links` は、実行前にビルドする（古い `dist/` を検査しないため）。

### D-036 AWS・デプロイの実装方針（2026-10-09、Phase 8）

- **OIDC の信頼条件**は environment で絞る：`sub` が `repo:higuma-lab/higuma-lab-web:environment:production` と完全一致するときだけ、デプロイ用ロールを引き受けられる。
  - **GitHub の environment `production` の Deployment branches を `main` だけに限ることが必須**（オーナーが設定。infra/README.md 手順6）。これを緩めると、他のブランチから本番にデプロイできるようになる。
  - environment を使う理由：デプロイの履歴が GitHub に残り、後から承認者（Required reviewers）を付けられるため。
- **環境依存の値**（ドメイン、リポジトリ名、environment 名）は `infra/.env`（コミットしない）から読む。アカウント ID は実行時のプロファイルから求める。メール用の DNS レコードは公開される値のため `infra/config/mail.ts` にコミットする（値は Zoho の登録後。今は空で、レコードを作らない）。
- **リージョンをまたぐ参照**（ホストゾーン → us-east-1 の証明書 → CloudFront）は CDK の `crossRegionReferences` を使う。CDK が SSM パラメーターとカスタムリソースの Lambda を作る（費用はほぼ0）。手作業で ID を受け渡す手順をなくすため。証明書を作り直すときは2段階の手順が要る（infra/README.md）。
- **GitHub の OIDC プロバイダー**は、カスタムリソースではなく CloudFormation のネイティブのリソース（`OidcProviderNative`）で作る。
- **CloudFront Function**：apex 以外のホスト（www、`*.cloudfront.net`）は apex へ 301。`/path/` は `index.html` を読み、拡張子のない `/path` は `/path/` へ 301。リダイレクト先は常に絶対 URL（`//evil.example` のようなパスで別ドメインへ飛ばないため）。
- **404**：OAC に ListBucket も許可し、存在しないパスを 404 として受けて `/404.html` を返す。一覧が返らないよう `defaultRootObject` も指定する。
- **価格クラス**は PRICE_CLASS_200（日本のエッジを含む。100 は北米・欧州のみ）。無料枠内の見込みは変わらない。
- **CSP** は自サイトと Cloudflare Web Analytics だけを許可し、`'unsafe-inline'` を使わない（D-032）。ビルド結果の全ページで違反0を確認した（解析のスクリプトを含む）。Permissions-Policy でカメラ・マイク・位置情報等を止める。
- **キャッシュ**：`_astro/` は1年・immutable、それ以外は `max-age=0, s-maxage=86400`。デプロイ時に `/*` を無効化し、完了を待ってから古いアセットを消す。
- **CI** は PR で実行する（design.md 7.4 の「main 以外への push」は、PR と二重に動くため外した）。E2E とリンク切れも CI に含める。deploy.yml は CI を呼び出し、通過してからデプロイする。
- `AWS_DEPLOY_ROLE_ARN` が未設定の間は、デプロイのジョブを飛ばす（AWS の構築前に main へマージしても失敗にしない）。
- CDK・GitHub Actions の依存はバージョンを固定する（Action はコミット SHA）。自動更新（Dependabot）は入れていない。

### D-037 Phase 9 の後の進め方と、プロフィールの記載（2026-10-10）

  - GitHub Issues は使わない。リポジトリの公開後は誰でも読めるため、公開しない確認事項を書けないから。
- プロフィールの経歴は、経験した技術と仕事の種類（Windows アプリ、通信・制御のソフトウェア、テストの自動化、チームでの開発）だけを書き、勤務先を推測させる記載は書かない（D-009 を補う）。

### D-038 構築記録の記事の書き方（2026-10-13）

- Claude Code を使って作ったことを、はっきり書く（D-016 の未決事項）。1本目の中心のテーマにする。
- **人が読む想定で書く**。AI による要約を前提にした長文にはしない。
  - 理由：読者には相談を考えているお客様（IT に詳しくない人も含む）がいて、要約では判断の理由や書き手の言葉が落ちやすい。見出しと段落が整理された記事は、AI でも要約しやすい。
- **1本目は 3,000 文字前後**（読む時間 5〜6 分）。冒頭に3行ほどの要約を置く。
  - 中身は「何を作ったか」「AI とどう分担したか」「気をつけたこと・感想」。技術の話は印象に残るものを2〜3個だけ短く。
- 技術の詳しい話（CSP、CDK と CloudFront、AI のレビューで見つかった問題など）は、2本目以降の候補にする。書くかどうかは後で決める。1本目だけでも成り立つようにする。
- オーナーが書く部分（書き出し・感想・おわり）は、Claude Code が質問を出し、オーナーの答えから文章の案を作る（インタビュー形式）。最終的な言い回しはオーナーが直す。
- 公開はサイトの公開と同時にし、AWS の構築作業で分かった事実（かかった時間、困ったこと、最初の請求額）も加える。

### D-039 対応地域と経験年数の載せ方（2026-10-14）

- 対応地域は「全国（オンライン・メールで対応）」とし、所在地（都道府県）は載せない（D-009 の「活動地域（都道府県）を公開する」を変更）。打ち合わせはオンラインかメールで行う（使うツールは決めていない）。
  - 理由：対面はほぼ想定していないため、地域名を載せると「近くなら訪問してくれる」と受け取られやすい。
  - 対面の希望については、FAQ 等に書かない。
- 経験年数は「15年以上」と、区切りのよい年数でぼかす。
  - 理由：正確な年数は毎年の更新が要り、ほかの情報と組み合わさると手がかりになるため（D-037）。年数が増えたら見直す。

### D-040 料金（2026-10-14）※D-010 を確定

相場を調べたうえで決めた（主な出典は、スキルマーケットの出品、個人の制作者の料金を解説する記事、制作会社の料金表。2026-10 時点）。実績が増えたら見直す。

- **ご依頼前のご相談・お見積もりは無料**（メールのやり取り、またはオンラインで 30 分程度まで）。それを超える相談や継続的な相談は、IT相談として有料（相談そのものもサービスにする）。
- **時間単価：1 時間 5,000 円**（以降 30 分ごとに 2,500 円）。IT相談・AI活用支援・Webサイト制作の指導・サポート・アプリ開発支援・公開後の更新と保守に共通。
  - 相場：個人向けの IT 相談は 30 分 1,000〜5,500 円、AI の個別レッスンは 60 分 7,500〜9,500 円、Web 作成の個別指導は 1 回 4,000〜9,900 円。実績づくりを優先し、中ほどに置いた。
- **Webサイト制作：10 万円〜**。5 ページまで、スマートフォン対応、ひぐま開発室の基本デザインを合わせて整える、構成の提案と文章の整え（原稿・写真はお客様）、修正はデザイン 2 回・公開前の文章 2 回、検索向けの基本設定、お問い合わせはメールのリンク。納期は 1〜1.5 か月が目安。
  - 別料金：ページの追加 1 ページ 1 万円〜、フォーム・完全オリジナルのデザインはお見積もり、更新・保守は時間単価、ドメイン・サーバーは実費（お客様の名義）。
  - 相場：個人の制作者の 5 ページ程度のサイトは 5 万〜30 万円（東京は 10 万〜30 万円）。下のほうに置いた。
  - デザインは、このサイトの部品を元にした「基本デザイン」を作って使い回す（既製のテーマやサイト作成サービスのテンプレートは使わない）。基本デザインができるまで、サイトには「基本デザイン」と書かない。サイトの置き場所と公開後の更新の方法は、お客様ごとに相談する。
  - 修正回数は「まとめて連絡された1回分を1回」と数える。納期は原稿と写真がそろってからの目安。
- **アプリ開発：お見積もり**（機能を絞った小さなツールで 10 万円〜を目安として示す）。
- **モニター募集**：Webサイト制作を 5 万円で先着 2 件（`src/data/pricing.ts` の `open` で受付終了を表示する）。条件は、制作物としてこのサイトに掲載すること（お名前の出し方は相談）と、公開後の感想。掲載が難しい場合は通常のお見積もり。
  - 「通常 10 万円 → 5 万円」のような割引の見せ方はしない。通常の料金での販売実績がないため、景品表示法の二重価格表示の問題になるおそれがある。条件の違う別のプランとして示す。
- 表示はすべて税込みの総額。課税事業者になったら（インボイスの登録など）見直す。
- 同時に引き受けられる件数に限りがあることを書き添える。
